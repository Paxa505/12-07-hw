## Задание 1

### Активный master-сервер и пассивный репликационный slave-сервер

В схеме «активный master — пассивный slave» все операции изменения данных (`INSERT`, `UPDATE`, `DELETE`) выполняет master-сервер. Slave-сервер получает изменения от master и поддерживает копию базы данных.

Основные преимущества:

- **Отказоустойчивость.** Если master перестанет работать, slave можно назначить новым master, и работа сервиса продолжится.
- **Резервное копирование данных.** На slave постоянно хранится актуальная или почти актуальная копия базы.
- **Снижение нагрузки на master.** Часть запросов на чтение можно направить на slave.
- **Простота администрирования.** Запись выполняется только на одном сервере, поэтому проще контролировать целостность и порядок изменения данных.
- **Обслуживание без остановки сервиса.** Резервное копирование, аналитические запросы и обновления можно выполнять на slave, не мешая работе master.

Недостаток схемы: все операции записи по-прежнему выполняет один master, поэтому такая архитектура масштабирует чтение, но не запись.

### Master-сервер и несколько slave-серверов

В этой схеме master принимает все операции записи, а несколько slave-серверов получают реплику данных и обслуживают запросы на чтение.

Основные преимущества:

- **Горизонтальное масштабирование чтения.** Чем больше slave-серверов, тем больше одновременных запросов на чтение может обработать система.
- **Балансировка нагрузки.** Запросы на чтение распределяются между master и несколькими репликами.
- **Высокая доступность.** При отказе master один из slave может быть повышен до нового master.
- **Надёжность хранения данных.** Копии базы находятся на нескольких серверах, поэтому отказ одного узла не приводит к потере всех данных.
- **Гибкое масштабирование.** Можно добавлять новые slave-серверы по мере роста нагрузки.
- **Разделение задач.** Один slave можно использовать для отчётов и аналитики, другой — для резервного копирования, а третий — для обслуживания пользователей.

Недостаток: master остаётся единственной точкой записи, поэтому при очень высокой нагрузке на запись потребуется шардирование базы данных.

## Задание 2

### План горизонтального и вертикального шардирования

База данных состоит из трёх таблиц:

- `users` — пользователи;
- `books` — книги;
- `shops` — магазины.

Предлагается использовать два подхода:

- **Вертикальное шардирование** — разные таблицы размещаются в разных базах данных.
- **Горизонтальное шардирование** — строки одной таблицы распределяются между несколькими базами данных по определённому ключу.

### Структура таблиц

```sql
CREATE TABLE users (
    user_id BIGINT PRIMARY KEY,
    email VARCHAR(255),
    name VARCHAR(255),
    created_at TIMESTAMP
);

CREATE TABLE shops (
    shop_id BIGINT PRIMARY KEY,
    name VARCHAR(255),
    city VARCHAR(255),
    owner_user_id BIGINT
);

CREATE TABLE books (
    book_id BIGINT PRIMARY KEY,
    title VARCHAR(255),
    author VARCHAR(255),
    price NUMERIC(10, 2),
    shop_id BIGINT
);
```

### Вертикальное шардирование

Таблицы разделяются по функциональным доменам:

| База данных | Таблицы | Назначение |
|---|---|---|
| `users_db` | `users` | Данные пользователей |
| `shops_db` | `shops` | Данные магазинов |
| `books_db` | `books` | Каталог книг |

Такое разделение позволяет масштабировать каждую часть системы независимо. Например, если нагрузка на каталог книг вырастет, можно добавить ресурсы только для `books_db`, не затрагивая базу пользователей.

### Горизонтальное шардирование

Таблица `users` делится по ключу `user_id`:

```text
users_shard_0: user_id % 3 = 0
users_shard_1: user_id % 3 = 1
users_shard_2: user_id % 3 = 2
```

Таблица `books` делится по ключу `shop_id`:

```text
books_shard_0: shop_id % 2 = 0
books_shard_1: shop_id % 2 = 1
```

Таблица `shops` на начальном этапе может храниться в одной базе данных с репликами. При росте числа магазинов её также можно разделить по `shop_id` или по региону.

### Блок-схема

```text
                         ПРИЛОЖЕНИЕ / API
                                   |
                          API Gateway / Router
                                   |
        +--------------------------+--------------------------+
        |                          |                          |
   users_router              shops_router              books_router
        |                          |                          |
+---------------+        +----------------+        +-------------------+
| users_db      |        | shops_db       |        | books_db          |
|               |        |                |        |                   |
| Master U0     |        | Master S0      |        | Master B0         |
| Replica U1    |        | Replica S1     |        | Replica B1        |
| Replica U2    |        +----------------+        | Replica B2        |
+---------------+                                    +-------------------+

Горизонтальные шарды users_db:
  users_shard_0 -> user_id % 3 = 0
  users_shard_1 -> user_id % 3 = 1
  users_shard_2 -> user_id % 3 = 2

Горизонтальные шарды books_db:
  books_shard_0 -> shop_id % 2 = 0
  books_shard_1 -> shop_id % 2 = 1
```

### Режимы работы серверов

- **Master (primary):** принимает все операции записи: `INSERT`, `UPDATE`, `DELETE`.
- **Replica / slave (standby):** получает изменения от master и обслуживает запросы на чтение.
- **Router / proxy:** определяет, в какой шард направить запрос, например по `user_id % 3` или `shop_id % 2`.
- **Резервный master:** в обычном режиме работает как replica, а при отказе основного master становится новым master.

### Примеры маршрутизации

- Пользователь с `user_id = 17` находится в `users_shard_2`, так как `17 % 3 = 2`.
- Книги магазина с `shop_id = 24` находятся в `books_shard_0`, так как `24 % 2 = 0`.
- Создание нового пользователя выполняется на master соответствующего шарда, после чего изменение реплицируется на его slave-серверы.
- Поиск книг и просмотр каталога можно выполнять на replica, чтобы не нагружать master.
